# 声明式 UI 与数据驱动（Declarative UI）

> 这是视图轴"怎么渲染"的哲学根基。现代前端框架（React/Vue/Svelte）全都是声明式的，理解"为什么选声明式"，才能理解后面所有渲染机制（响应式、虚拟 DOM、重渲染控制）的存在理由。

## 是什么

构建 UI 有两种范式：

| 范式 | 思路 | 典型 |
|---|---|---|
| **命令式（Imperative）** | 你写"怎么操作 DOM"一步步达成结果 | jQuery、原生 DOM 操作 |
| **声明式（Declarative）** | 你描述"界面该长什么样"（状态的函数），框架负责更新 | React、Vue、Svelte |

声明式 UI 的核心模型只有一个公式：

```
UI = f(state)
```
**界面是状态的函数**——给定状态，UI 唯一确定。状态变，UI 自动更新，你不用手动操作 DOM。

一句话边界：**命令式描述"过程"（先 append 这个，再改那个 class），声明式描述"结果"（状态长这样，UI 就该长这样）。**

## 为什么：声明式为什么胜出

回到 [00-2 权衡](../../00-foundation/tradeoffs.md) 的第一组——这是前端最根本的权衡。命令式在"小规模"下更直观、更灵活，但**界面规模一大就失控**：

### 命令式的死穴：状态-DOM 一致性难维护
命令式要你**时刻保证 DOM 反映当前状态**。状态一复杂，你忘了某个分支该隐藏/显示、忘了某个值该更新，DOM 就和状态脱节——bug 的头号来源。

```
// 命令式：你要手动维护每处 DOM 和状态的一致
$.get('/api/user').then(user => {
  $('#name').text(user.name)
  if (user.vip) { $('#badge').show() } else { $('#badge').hide() }
  $('#avatar').attr('src', user.avatar)
  // ... 还有 20 处要同步，漏一个就 bug
})
```

### 声明式的承诺：一致性由框架保证
你只管维护 `state`，UI 怎么从 `state` 生成、`state` 变了怎么更新，框架全包。**心智负担从"维护无数处 DOM"降到"维护一个状态"**。

```
// 声明式：描述 UI 是 state 的函数，框架保证一致
function Profile({ user }) {
  return <div>
    <span>{user.name}</span>
    {user.vip && <Badge />}
    <img src={user.avatar} />
  </div>
}
```

### 声明式的代价（要知道你在用什么换什么）
- **框架开销**：框架要算"状态变了，DOM 该怎么变"，这有计算成本。
- **失控场景**：极致性能需求（高频动画、海量 DOM）下，声明式不如直接操作 DOM。
> 这个代价是值得的：用框架的开销，换来"状态-视图一致性"这个规模化下最贵的保证。详见 [01-9 性能与体验](../01-9-performance-ux/README.md)。

## 怎么工作：声明式的三层抽象

声明式 UI 靠三层抽象工作，每一层都是后续原子笔记的主题：

```
1. 状态变化       →  你改 state（框架知道状态变了）
2. 重新计算视图    →  f(state) 重新跑，得到新的"想要的 UI"
3. 应用到 DOM     →  框架对比新旧 UI，算出最小变更，更新 DOM
```

- 第 1 步"框架怎么知道状态变了" → [响应式原理](./reactivity.md)
- 第 3 步"怎么算最小变更" → [虚拟 DOM 与调和](./virtual-dom.md)
- "怎么减少无谓的计算" → [重渲染控制](./re-render-control.md)

## 常见坑

- ❌ **在声明式框架里写命令式代码**：用 React 但在 effect 里手动 `document.getElementById` 操作 DOM，破坏一致性保证。
  - ✅ 正例：用状态驱动，DOM 操作交给框架；确需操作 DOM 用 ref 而非全局查询。
- ❌ **以为声明式万能**：所有动画/Canvas/性能极致场景都用声明式套，导致卡顿。
  - ✅ 正例：声明式是默认选择；性能敏感场景（如高频动画）用命令式或更细粒度方案。
- ❌ **状态和 DOM 双重管理**：一边维护 state，一边又手动改 DOM，两者打架。
  - ✅ 正例：DOM 是状态的派生物，单一数据源，DOM 只读不手动改。
