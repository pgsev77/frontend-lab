# 虚拟 DOM 与调和（Virtual DOM & Reconciliation）

> "状态变了，新 UI 算出来了，但怎么把它高效地应用到真实 DOM？"——虚拟 DOM 是 React 给出的答案。理解它，才能理解 diff、key、以及为什么 React 性能有时不如细粒度响应式。

## 是什么

- **虚拟 DOM（Virtual DOM）**：真实 DOM 的**轻量 JS 对象描述**。用普通对象表示"这里该有个 `<div>`，属性是这些，子节点是那些"，不直接碰真实 DOM。
- **调和（Reconciliation）**：拿到"新虚拟 DOM 树"和"旧虚拟 DOM 树"，**对比找出差异（diff）**，然后把差异最小化地应用到真实 DOM 的过程。

一句话边界：**虚拟 DOM 是"草稿"，调和是"对比草稿找差异并落笔"。** 两者配合，让"声明式 UI"在状态变化后高效更新真实 DOM。

## 为什么：为什么不直接操作真实 DOM

[01-1 DOM 模型](../01-1-view-fundamentals/dom-model.md) 讲过：真实 DOM 操作很贵（触发重排/重绘）。如果状态一变，就把整个页面重新生成真实 DOM，性能灾难。

虚拟 DOM 的思路：**先在内存（轻量 JS 对象）里算出"想要的 UI"，对比新旧版本，只把真正变化的部分应用到真实 DOM**。这样：
- 大量计算发生在便宜的 JS 对象层。
- 真实 DOM 只被精确触碰最小次数。

### 代价：diff 本身也有成本
虚拟 DOM 不是免费午餐。对比两棵树本身要花时间。而且**精确对比两棵树的差异是 O(n³)**——对大型 UI 不可接受。所以 React 用了三条启发式假设，把复杂度压到 O(n)。

## 怎么工作：调和算法的三条假设（★ 核心）

把树对比从 O(n³) 降到 O(n)，靠三条假设：

### 假设 1：不同类型的元素，直接替换（不比较子树）
```
旧: <div>...</div>   新: <span>...</span>
→ 类型不同，销毁整个 <div> 子树，新建 <span>。不尝试复用。
```

### 假设 2：同类型元素，保留 DOM 节点，只更新变化的属性
```
旧: <div class="a">  新: <div class="b">
→ 复用同一个 DOM 节点，只改 class。
```

### 假设 3：列表靠 `key` 标识身份，判断"是移动还是替换"（★ 最关键）
对比同级子节点列表时，框架默认按**位置顺序**对比——但列表顺序变化（插入/删除/排序）会导致大量误判。`key` 给每个元素一个**稳定身份**：

```
旧列表:  [A, B, C]      （key 分别 a,b,c）
新列表:  [D, A, B, C]   （头部插入 D）

❌ 不用 key（按位置对比）：D 顶掉 A 的位置 → A 变 D、B 变 A... 全乱套
✅ 用 key：发现 a/b/c 都还在，只是整体后移，D 是新增 → 只插入 D，其余复用
```

**为什么不能用数组 index 当 key**：index 不稳定——列表插入一个元素，所有 index 都变了，框架以为所有元素都"变了"，全部重建，性能差且可能引发 [状态错位 bug](./re-render-control.md)（组件内部状态串到别的项上）。

## 常见坑

- ❌ **用 index 当 key**：列表一变动，性能差 + 状态串项。
  - ✅ 正例：用数据本身的稳定唯一 ID 当 key。
- ❌ **随机值当 key**（如 `Math.random()`）：每次渲染 key 都变，等于全重建，失去虚拟 DOM 的意义。
- ❌ **以为虚拟 DOM 比直接操作 DOM 快**：错。虚拟 DOM 是"声明式一致性"的代价，不是性能优势。直接精细操作 DOM 仍是最快的，只是不可维护。
- ❌ **在列表中间插入元素却不用 key**：导致输入框/选中态等组件内部状态错位（跟着位置走而非跟着数据走）。
