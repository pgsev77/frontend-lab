# 渲染时机与调度（Rendering Scheduling）

> "状态变了，框架什么时候去更新 DOM？"——不是立即，而是有调度策略。理解调度，才能理解 React 的并发渲染、Suspense、transition 这些特性的存在理由。

## 是什么

渲染调度指框架**决定"什么时候渲染、以什么优先级渲染、能不能被打断"**的机制。它是渲染机制的"时间层"——前面讲的是"怎么算"，这篇讲"什么时候算"。

两种模式：

| 模式 | 特点 | 代表 |
|---|---|---|
| **同步渲染** | 一旦开始渲染就一口气跑完，不可打断 | 早期 React、Vue 默认 |
| **并发渲染（Concurrent）** | 渲染可中断、可恢复、可按优先级调度 | React 18+ |

一句话边界：**同步渲染是"一锤子买卖"，并发渲染是"可随时暂停让路"。**

## 为什么：为什么需要调度

### 痛点：长任务阻塞交互
同步渲染下，一个组件树很大时，渲染可能耗时几十甚至上百毫秒。这期间主线程被占满，**用户的点击/输入得不到响应**——界面"卡住"。这就是 [01-9 性能](../01-9-performance-ux/README.md) 里"长任务"问题的渲染层根源。

### 解法：让渲染可中断
并发渲染把渲染拆成小单元（Fiber），每处理一个单元就**检查"有没有更高优先级的任务（如用户输入）"**，有的话就暂停渲染、先处理交互，处理完再恢复渲染。

```
同步渲染:  [===== 大渲染 50ms，期间用户点击无响应 =====] → 响应点击
并发渲染:  [= 渲染][响应用户输入][= 继续渲染...] → 点击立即响应，渲染延后
```

> 直觉：**用户输入的优先级 > 数据更新的优先级**。调度让框架能"插队"处理高优先级的事。

## 怎么工作

### Fiber 架构（React）
Fiber 把组件树拆成**可中断的工作单元链表**。每个 Fiber 节点记录"渲染到哪了"，这样中断后能从断点恢复，不用从头算。这是并发渲染的物理基础。

渲染分两阶段：
1. **Render 阶段**（可中断）：算出新的虚拟 DOM，纯计算，无副作用。
2. **Commit 阶段**（不可中断）：把变更应用到 DOM，跑副作用（useLayoutEffect/useEffect）。
> 关键：只有 Render 阶段可中断；Commit 阶段必须一气呵成，保证 DOM 一致性。

### 并发特性
- **useTransition**：把某个状态更新标记为"低优先级"（如切 Tab 时的大列表渲染），让用户输入永远优先。
```
const [isPending, startTransition] = useTransition()
// 搜索结果更新是"可延后"的，输入框始终流畅
function onChange(e) {
  setQuery(e.target.value)                 // 高优先级：输入框立即更新
  startTransition(() => setResults(search)) // 低优先级：结果可延后渲染
}
```
- **Suspense**：渲染时遇到"还没准备好的数据/组件"，挂起并显示 fallback，等准备好再渲染。配合并发渲染，做到"流水线式"渲染。
- **优先级**：框架给不同更新打标签（用户输入 > 数据请求 > 过渡动画），按优先级调度。

## 常见坑

- ❌ **以为状态一变 DOM 立即更新**：状态变到 DOM 更新之间有调度延迟，依赖"立即更新"的逻辑（如更新后立即读 DOM 尺寸）可能出错。
  - ✅ 正例：用 useEffect/useLayoutEffect 在 commit 后操作 DOM。
- ❌ **滥用并发特性**：给所有更新都套 transition，反而拖慢正常更新。transition 只用于"可延后"的大渲染。
- ❌ **在 Render 阶段做副作用**（如改全局变量、发请求）：并发渲染下 Render 可能中断重启，副作用会执行多次或乱序。
  - ✅ 正例：副作用放 useEffect（Commit 阶段）。
