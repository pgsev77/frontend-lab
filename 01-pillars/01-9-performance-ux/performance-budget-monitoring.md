# 性能预算与监控（Performance Budget & Monitoring）

> 性能不是"做一次优化就完了"，它会随时间劣化——加个新功能、引个新依赖，包变大了、变慢了。性能预算和持续监控让性能**不回归**，是工程化保障。

## 是什么

- **性能预算（Performance Budget）**：为性能指标设上限（如首屏 JS 不超 200KB、LCP 不超 2.5s），超了就报警/阻断。
- **性能监控**：持续观测真实用户的性能数据，发现回归。

一句话边界：**预算是"事前设红线"，监控是"事后持续盯"。两者让性能从"一次性优化"变成"长期纪律"。**

## 为什么：性能会回归

性能有个残酷规律：**不持续守护，必然劣化**。
- 新功能加代码 → 包变大。
- 新依赖引入 → 可能几 MB。
- 新人不懂优化 → 写了 N+1 渲染。
- 没人管 → 半年后 LCP 从 2s 变 5s。

没有预算和监控，性能回归要等"用户投诉"或"偶然发现"，为时已晚。预算+监控把性能变成**可度量、可卡控**的工程指标。

## 怎么用

### 1. 设性能预算
为关键指标定上限，常见的预算维度：
| 维度 | 示例预算 |
|---|---|
| JS 包体积 | 首屏 < 170KB（gzip） |
| LCP | < 2.5s |
| INP | < 200ms |
| CLS | < 0.1 |
| 请求数 | 首屏 < 50 |
| 图片 | 单张 < 100KB |

预算要**现实**（基于当前基线定，而非拍脑袋），并**分页面**（首页和详情页预算可不同）。

### 2. 在 CI 里卡预算（质量门禁）★
把预算变成 CI 检查，超了**构建失败**，强制开发者处理：
- **bundle 体积**：用 `size-limit`、`bundlewatch`，包超预算则 CI 失败。
- **Lighthouse CI**：跑 Lighthouse，分数/指标不达标则失败。
- **类型检查/测试**：见 [01-13 质量门禁](../01-13-observability-quality/README.md)。
> 门禁的关键：**超预算不让合并**，而非"警告一下继续"。否则形同虚设。

### 3. 真实用户监控（RUM）★
用 RUM 采集**真实用户**的性能数据（不是实验室 Lighthouse），因为真实用户环境千差万别（弱网、低端机）：
```
// 用 web-vitals 库采集真实用户的 CWV
import { onLCP, onINP, onCLS } from 'web-vitals'
onLCP(metric => report(metric))   // 上报真实用户的 LCP
onINP(metric => report(metric))
onCLS(metric => report(metric))
```
- 上报到监控平台（自建或 Sentry/Datadog）。
- **按维度分**：看整体平均会掩盖问题，要按设备/网络/地区分（低端机用户可能特别慢）。

### 4. 实验室监控（合成监控）
定时用 Lighthouse 跑固定脚本，监控回归。优点：稳定可复现；缺点：不代表真实用户。与 RUM 互补。

### 5. 性能告警
指标回归时告警：
- LCP P75 突然从 2s 升到 4s → 告警。
- 新版本发布后 INP 劣化 → 自动回滚或介入。

## 常见坑

- ❌ **只优化不守护**：做完一次性优化，没有预算/监控，半年后回归原样。
- ❌ **门禁只警告不阻断**：超预算警告一下还让合并，等于没门禁。
- ❌ **只看实验室数据忽视 RUM**：Lighthouse 分高，但真实弱网用户极慢。
- ❌ **预算拍脑袋**：定个不切实际的预算（如首屏 50KB），团队永远达不到，预算被无视。
  - ✅ 正例：基于当前基线，渐进式收紧。
