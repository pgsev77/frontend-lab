# 依赖安全（Supply Chain Security）

> 现代前端几乎全靠第三方包构建——但每个依赖都是潜在的攻击面。包被投毒、依赖有漏洞、CDN 被篡改，都可能让你"写的代码很安全，但应用被攻破"。

## 是什么

依赖安全指**管理第三方依赖带来的风险**，包括：
- **漏洞依赖**：依赖的包有已知安全漏洞。
- **恶意包**：攻击者发布的恶意包（窃取数据、植入后门）。
- **供应链攻击**：包作者账号被盗、构建流程被入侵，发布带毒的"新版本"。
- **CDN 篡改**：从 CDN 加载的脚本被替换。

一句话边界：**你的安全性 ≤ 最弱的依赖的安全性。** 一个有漏洞的依赖能让整个应用沦陷。

## 为什么：npm 生态的供应链风险

npm 生态的特点放大了风险：
- **依赖树极深**：一个项目可能间接依赖上千个包（依赖的依赖），你只直接装几十个，但传递依赖爆炸。
- **发布无审核**：任何人都能发 npm 包，包名可刻意模仿（typosquatting，如 `reactt` 冒充 `react`）。
- **账号盗用**：维护者账号被盗后发布带毒版本。
- 历史 case：event-stream、ua-parser-js 等知名包曾被植入恶意代码，影响海量项目。

## 怎么用：五种防护

### 1. 锁定版本（lockfile）★
`package-lock.json`/`pnpm-lock.yaml` 锁定**每个依赖的确切版本和来源**，避免"今天装的和昨天装的不一样"（传递依赖偷偷更新带毒版本）：
- 提交 lockfile 到版本库。
- CI 用 `npm ci`（严格按 lockfile 装）而非 `npm install`（可能解析新版本）。
- 锁定版本后，至少保证"测试过的依赖"和"线上跑的依赖"一致。

### 2. 漏洞审计
定期扫描依赖的已知漏洞：
```
npm audit              # 扫描漏洞
# 或用 Snyk、Dependabot、Renovate 自动发现 + 提 PR 升级
```
- 发现有漏洞的依赖及时升级或换替代。
- GitHub 的 Dependabot 可自动监测并提升级 PR。

### 3. 子资源完整性（SRI）
从 CDN 加载脚本时，加 `integrity` 属性（资源的 hash），CDN 被篡改时浏览器拒绝执行：
```
<script src="https://cdn.example.com/lib.js"
        integrity="sha384-abc123..."
        crossorigin="anonymous"></script>
<!-- CDN 内容变了，hash 不匹配，浏览器不执行 -->
```

### 4. 审查新依赖
引入新依赖前：
- **必要性**：真需要吗？能自己写几十行解决就别引包。
- **可信度**：下载量、维护活跃度、作者信誉、有无已知问题。
- **依赖数**：它自己又引了多少依赖（依赖树越浅越安全）。
- 警惕**包名模仿**（typosquatting），确认拼写正确。

### 5. 限制动态加载第三方脚本
动态 `inject` 第三方脚本（统计、广告）要谨慎——这些脚本能访问 DOM、Cookie。优先用 CSP（[CSP](./csp.md)）限制可加载的源。

## 常见坑

- ❌ **不提交 lockfile**：不同环境装的依赖版本不一致，可能引入带毒版本。
- ❌ **从不审计漏洞**：依赖一堆已知漏洞包，浑然不觉。
- ❌ **CDN 脚本不加 SRI**：CDN 被篡改，加载恶意脚本。
- ❌ **随意引入大依赖**：一个工具函数引一个 100KB 的包，还带来深层依赖。
- ❌ **不限制第三方脚本源**：任意域名脚本能加载，攻击面失控。
