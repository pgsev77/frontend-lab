# 前端鉴权与令牌存储（Auth & Token Storage）

> "登录 token 存哪？"——这是前端安全的高频争论题。localStorage 简单但 XSS 可偷，Cookie 安全但 CSRF 风险。这篇讲透令牌存储的权衡，以及双令牌模式怎么兼顾安全与体验。

## 是什么

前端鉴权指**证明"我是登录用户"**的机制，通常用令牌（Token）。令牌存储指**这个令牌放哪里**。四个候选位置：

| 存储位置 | XSS 能偷吗 | CSRF 风险 | 持久性 |
|---|---|---|---|
| **localStorage** | ✅ 能（JS 可读） | 无（不自动携带） | 持久 |
| **sessionStorage** | ✅ 能 | 无 | 关标签即失 |
| **Cookie（HttpOnly）** | ❌ 不能（JS 读不到） | ✅ 有（自动携带） | 可控 |
| **内存（JS 变量）** | ❌ 不能 | 无 | 刷新即失 |

一句话边界：**存储位置决定"防 XSS 还是防 CSRF"的侧重**——没有完美选项，只有权衡。

## 为什么：存储位置的权衡

### localStorage：简单但 XSS 致命
最常见但最脆弱。一旦站点有 XSS（[XSS](./xss.md)），恶意脚本能 `localStorage.getItem('token')` 直接读走令牌，冒充用户。

### HttpOnly Cookie：防 XSS 但引 CSRF
JS 读不到（防 XSS 偷取），但浏览器**自动携带**到每个同源请求（[CSRF](./csrf.md) 温床）。配 `SameSite` + CSRF token 缓解。

### 内存：最安全但刷新丢
令牌只存在 JS 变量里，XSS 在变量被垃圾回收前也未必找得到，刷新页面就丢。需配合"刷新令牌"机制（见下）自动重新登录。

> 关键认知：**没有绝对安全的存储，只有"提高攻击成本"的组合策略。**

## 怎么用：双令牌模式 ★ 工业最佳实践

### 访问令牌（Access Token）+ 刷新令牌（Refresh Token）
```
访问令牌：短期有效（如 15 分钟），用于 API 鉴权
刷新令牌：长期有效（如 7 天），只能用来"换新的访问令牌"
```
**分工**：
- 访问令牌暴露面大（每个请求带），所以短命——即使泄露，15 分钟后失效。
- 刷新令牌暴露面小（只在访问令牌过期时用一次），所以可以长期。

### 存储组合（推荐）
```
访问令牌 → 内存（最安全，刷新即失）
刷新令牌 → HttpOnly Cookie（JS 读不到，且只用于换 token 这一个端点）
```
- 访问令牌在内存，XSS 难偷，刷新就丢——丢了大不了重新用刷新令牌换。
- 刷新令牌在 HttpOnly Cookie，XSS 读不到；且只在 `/refresh` 端点用，配合 SameSite 防 CSRF。
- 用户体验：访问令牌过期时，前端用刷新令牌静默换新，用户无感。

### 令牌过期与刷新流程
```
请求 API → 401（访问令牌过期）
  → 自动调 /refresh（用 Cookie 里的刷新令牌）
    → 拿到新访问令牌，存内存
      → 重试原请求（用户无感）
```
**并发刷新问题**：多个请求同时发现过期，会同时触发多次 /refresh。用"单飞"模式——只发一次刷新，其他请求等它完成。

## 常见坑

- ❌ **访问令牌存 localStorage**：XSS 一发，token 泄露，冒充用户。
  - ✅ 正例：访问令牌存内存，刷新令牌存 HttpOnly Cookie。
- ❌ **令牌永不过期**：一旦泄露永久有效。访问令牌必须短命。
- ❌ **刷新令牌端点不做 CSRF 防御**：刷新令牌在 Cookie，/refresh 端点仍需 CSRF 防护。
- ❌ **并发刷新风暴**：多请求同时刷新，浪费且可能让旧刷新令牌失效。
