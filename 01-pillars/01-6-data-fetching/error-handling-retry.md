# 错误处理与重试（Error Handling & Retry）

> "请求失败了怎么办"——这是 [异步四态](./async-four-states.md) 里 error 态的展开。网络不可靠是常态（[前端本质](../../00-foundation/frontend-essence.md) 差异 3），错误处理决定了用户在失败时是"能自救"还是"无奈离开"。

## 是什么

错误处理与重试指**请求失败时如何识别错误类型、如何反馈用户、如何自动/手动重试**。它是 [异步四态](./async-four-states.md) 的 error 分支的完整处理。

一句话边界：**错误处理的目标不是"消灭错误"（网络必失败），而是"让失败可理解、可恢复"。**

## 为什么：错误有三类，处理不同

请求失败不是单一情况，要分清类型，分别处理：

| 错误类型 | 含义 | 处理 |
|---|---|---|
| **网络错误** | 断网/超时/服务器无响应 | 可重试（临时故障） |
| **服务端错误** | 5xx（服务器自己崩了） | 可重试（服务可能恢复） |
| **业务错误** | 4xx（参数错/权限不足/余额不足） | **不重试**（重试也一样） |

**关键区分**：网络/服务端错误是"临时故障"，重试有意义；业务错误是"请求本身有问题"，重试无意义，只会更糟。把业务错误当网络错误狂重试，是常见错误。

## 怎么用

### error 态的界面（呼应四态）
错误时不能只显示"出错了"，要给用户**理解和自救的途径**：
```
case 'error':
  return <ErrorView
    message={友好描述错误}        // "网络异常"，不是 "TypeError: ..."
    onRetry={refetch}              // ★ 重试按钮（最关键的自救入口）
  />
```
- 错误信息要**人类可读**（不是堆栈），区分"网络问题"还是"操作不被允许"。
- **提供重试入口**——临时故障用户点重试就好，这是 error 态最重要的设计。

### 自动重试（针对临时故障）
网络/服务端错误可自动重试，但要用**指数退避**，避免雪崩：
```
// TanStack Query 内置重试
{ retry: 3, retryDelay: attempt => Math.min(1000 * 2**attempt, 30000) }
// 第1次等2s，第2次4s，第3次8s（指数退避，避免压垮服务器）
```
**指数退避**为什么重要：如果服务器过载，所有客户端同时重试会让它更过载（雪崩）。退避让重试错开，给服务器喘息。

### 业务错误不重试
业务错误（4xx）重试无意义，要明确排除：
```
{ retry: (failCount, error) => error.status >= 500 }  // 只重试 5xx
```

### 优雅降级（partial failure）
部分数据失败时，不要让整页崩溃，而是**展示可用部分 + 标注失败部分**：
```
页面有 3 个数据块，其中 1 个请求失败：
❌ 整页显示 error（用户什么都看不到）
✅ 显示成功的 2 个块 + 失败的块显示"加载失败，点击重试"
```
这是 [防御性哲学](../../00-foundation/frontend-essence.md) 的体现——局部失败不拖垮整体。

### 错误边界兜底
未捕获的渲染错误（如 data 为 null 时访问 data.x）会让组件树白屏。用错误边界（Error Boundary）兜住，显示降级 UI。详见 [01-13 可观测性](../01-13-observability-quality/README.md)。

## 常见坑

- ❌ **错误信息直接显示堆栈/技术细节**：用户看不懂，恐慌。
  - ✅ 正例：人类可读的描述 + 技术细节只记日志不上界面。
- ❌ **业务错误也自动重试**：权限不足、余额不足，重试只会一直失败。
  - ✅ 正例：区分错误类型，只重试临时故障。
- ❌ **重试不退避**：固定间隔重试，服务器过载时雪崩。
- ❌ **error 态没有重试按钮**：用户遇到临时故障无法自救，只能刷新整页。
- ❌ **一处失败整页崩溃**：一个数据块失败，整页白屏。
  - ✅ 正例：局部失败局部处理，优雅降级。
