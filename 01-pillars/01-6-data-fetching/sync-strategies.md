# 数据同步策略（Data Sync Strategies）

> 前端数据是"可能过时的副本"——那什么时候该重新拉取？拉太勤浪费资源，拉太少数据陈旧。这篇讲清"何时刷新"的各种策略，是 [客户端缓存](./client-cache.md) 的时序篇。

## 是什么

数据同步策略指**决定何时认为缓存过期、何时重新请求服务端**的规则。它回答"前端这份副本，怎么保持'足够新鲜'"。

一句话边界：**同步策略是在"数据新鲜度"和"请求成本"之间找平衡。** 实时同步最准但最贵，永不同步最省但数据陈旧。

## 为什么：为什么需要同步策略

前端缓存（[客户端缓存](./client-cache.md)）带来一个根本矛盾：**缓存越久越省请求，但越可能过时**。没有明确的同步策略，要么：
- 从不刷新 → 用户看到的永远是首次加载的旧数据。
- 无脑频繁刷新 → 每次操作都重拉，缓存失去意义，服务器压力大。

好的同步策略让数据"**在用户需要新数据时刚好够新，其余时候用缓存省请求**"。

## 怎么用：六种同步触发

### 1. stale-while-revalidate（基础）★
默认策略：先用缓存即时显示，后台静默刷新。用户不白屏 + 数据会更新。详见 [客户端缓存](./client-cache.md)。

### 2. 窗口聚焦时刷新
用户切回标签页（从别的标签/应用回来），大概率想看新数据，此时刷新：
```
useQuery(key, fn, { refetchOnWindowFocus: true })  // TanStack Query 默认开启
```
**为什么有效**：用户离开一段时间再回来，数据很可能已经变了。这个时机刷新，体验好且不浪费（用户真在看时才刷）。

### 3. 网络重连时刷新
断网恢复后刷新——用户离线期间数据可能变了，重连后拉最新：
```
{ refetchOnReconnect: true }
```

### 4. 轮询（polling）
定时刷新，适合需要"近实时"但不必 WebSocket 的场景：
```
{ refetchInterval: 5000 }  // 每 5 秒刷新一次
```
**代价**：请求频繁，服务器压力大。只用于真正需要近实时的数据（如监控看板）。

### 5. 手动失效（最精确）
执行了变更操作后，手动让相关缓存失效：
```
mutation 成功 → invalidateQueries(['orders'])  // 订单列表失效，自动重拉
```
这是**最精确**的策略——你知道数据肯定变了（刚改过），精准失效，不轮询不浪费。

### 6. 实时推送（WebSocket / SSE）
数据一变，服务端主动推过来更新缓存，达到真正的实时：
```
WebSocket 收到 'order:updated' → queryClient.setQueryData(['orders'], newData)
```
详见 [01-8 实时交互](../01-8-interaction-forms/README.md)。实时推送适合**多端共享、变化频繁**的数据（协作编辑、聊天、股票）。

## 怎么选：策略匹配场景

| 场景 | 推荐策略 |
|---|---|
| 普通列表/详情 | stale-while-revalidate + 窗口聚焦 + 变更后失效 |
| 监控/仪表盘 | 轮询（可接受延迟） |
| 协作/聊天/实时 | WebSocket 推送 |
| 低频变化（配置） | 长 staleTime，很少刷新 |
| 刚做完变更 | 手动失效（最精确） |

### staleTime 与 gcTime 的区别（易混）
- `staleTime`：数据多久内算"新鲜"（不触发后台刷新）。如 30s 内不刷。
- `gcTime`（旧 cacheTime）：缓存多久没被用就**从内存清掉**。如 5 分钟没访问就删。

> 前者管"要不要刷新"，后者管"要不要保留缓存"，别混。

## 常见坑

- ❌ **从不刷新**：数据永远停在首次加载，用户看到旧数据。
- ❌ **无脑轮询**：所有数据都轮询，服务器压力爆炸。只对真正需要的轮询。
- ❌ **变更后不失效**：提交了数据，列表不更新，用户以为没提交（呼应 [乐观更新](./optimistic-update.md) 的 onSuccess 失效）。
- ❌ **混淆 staleTime 和 gcTime**：以为设了 staleTime 就会清缓存，结果缓存堆积占内存。
