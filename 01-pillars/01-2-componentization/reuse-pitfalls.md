# 复用陷阱（Reuse Pitfalls）

> "DRY（不要重复）"是美德，但**过度追求复用是前端最大的陷阱之一**。很多"通用组件"最后变成谁都不敢动的上帝组件。这篇讲复用的三条红线：何时该复用、何时该忍住。

## 是什么

复用陷阱指**为了"将来可能复用"而提前抽象，或为了"消除重复"而强行合并**，结果制造出比重复更糟糕的东西——过度抽象、过度通用、难以维护的组件。

一句话边界：**重复不一定是问题，错误的抽象才是问题**。两处相似代码各自演进，通常比一个勉强通用却处处妥协的抽象更健康。

## 为什么：三条红线的根源

复用陷阱来自三种心态：

### 心态 1："以后可能要复用" → 过早抽象
在只有一处使用时，就猜测"将来别处也要用"，抽出带各种配置项的"通用组件"。结果：
- 真正的复用场景从未出现，通用组件白写。
- 即使出现了，需求细节不同，通用组件要不停加 prop 来适配，变成"配置怪兽"。

> 这违背 [YAGNI](../../00-foundation/tradeoffs.md)（You Aren't Gonna Need It）。**让重复先发生两三次，看清真实共性，再抽象。**

### 心态 2："这两处代码长得像" → 错误的抽象
两段相似代码不等于该合并。它们可能只是**巧合地相似**，但背后的业务意图不同。强行合并成一个通用组件后，两处需求开始分化，通用组件被迫加各种开关来兼顾，最终每处都要配一堆 `if/else` prop。

> 法则（Sandi Metz）：**重复比错误的抽象便宜得多**。错误的抽象一旦扩散，比重复难改十倍。

### 心态 3："这个组件要能应付所有场景" → 上帝组件
一个组件吃下几十个 props、无数配置，试图覆盖所有变体。结果是：
- 调用方要查文档才知道该设哪些 prop。
- 改一个 prop 的行为，可能波及无数调用方。
- 没人敢重构，因为影响面不可控。

## 怎么用：判断何时抽象

### 该抽象的信号（满足≥2 条再动手）
1. **真实的第三处复用**：已经第三次写几乎相同的代码（"三次法则"）。
2. **共性清晰且稳定**：这几处的核心意图确实一致，不是巧合相似。
3. **抽象后接口简单**：抽出来的东西 API 干净，不需要一堆开关。

### 不该抽象的信号
1. 只有"将来可能"用，现在只一处 → 等。
2. 几处代码表面像，但业务语义不同（如"用户列表"和"商品列表"结构像，但筛选/排序/权限逻辑不同）。
3. 抽象后需要大量条件分支才能适配各场景 → 抽象错了。

### 用"组合"代替"通用化"
当多个场景有差异时，别做一个超通用组件，而是：
- 抽出**稳定的公共骨架**（如布局壳）。
- 把**变化的部分**留作插槽/复合组件，让调用方自己填。
- 呼应 [组合优于继承](./composition-over-inheritance.md) 和 [组件 API 设计](./component-api.md)。

```
❌ 上帝组件：<SuperTable searchable paginated sortable exportable themed dense .../>
✅ 组合：<Table><SearchBar/><TableHead/><TableBody/><Pagination/></Table>
```

## 常见坑

- ❌ **见到重复就合并**：违反"三次法则"，过早抽象。
  - ✅ 正例：等重复稳定出现 3 次，看清真实共性再抽。
- ❌ **抽象后加开关消除差异**：通用组件里 `if (mode === 'a') ... else if (mode === 'b') ...` 越加越多。
  - ✅ 正例：差异大说明抽象边界错了，拆成多个聚焦组件或用组合。
- ❌ **不敢删过度抽象的组件**：因为"可能有人在用"，上帝组件一直留着。
  - ✅ 正例：勇敢地用更小的聚焦组件替换，配套迁移（呼应 [03 工程实践](../../03-engineering/README.md) 的变更流程）。
- ❌ **把"复用"当唯一目标**：为消除重复牺牲了可读性和可变性。
  - ✅ 正例：复用是手段，可维护性才是目标。适度重复是健康的。
