# 构建工具（Build Tools）

> 现代 JS 浏览器不直接跑你写的代码——TS 要编译、JSX 要转译、新语法要降级、CSS 要处理、代码要打包压缩。构建工具做这些。理解构建工具，才能理解"开发为什么快、生产为什么小"。

## 是什么

构建工具把**开发时的人体工学代码**（TS/JSX/新语法/模块化/SCSS）转换成**浏览器能高效运行的产物**。核心能力：

| 能力 | 作用 |
|---|---|
| **编译/转译** | TS→JS、JSX→JS、新语法→兼容语法 |
| **打包（bundle）** | 把分散模块合成少数文件（减少请求数） |
| **Tree-shaking** | 剔除未使用的代码 |
| **代码分割** | 按需拆分产物（[01-7 代码分割](../01-7-routing/code-splitting.md)） |
| **压缩** | 减小产物体积 |
| **Dev Server / HMR** | 开发热重载 |

一句话边界：**构建工具 = 把"好写的代码"变成"好运行的产物"。**

## 为什么：为什么需要构建

### 浏览器要的是"原生 JS"
你写 TS（有类型）、JSX（HTML in JS）、新语法（可选链等）、ES Modules。但浏览器：
- 旧浏览器不认新语法 → 要转译降级。
- 不认 TS/JSX → 要编译。
- 早期 ESM 兼容差/请求多 → 要打包合并。

不构建，要么只写老语法（开发体验差），要么手动处理（不可行）。

### 性能优化靠构建
- 打包合并减少请求数。
- Tree-shaking 删死代码，减小体积。
- 压缩 minify。
- 代码分割（[01-7](../01-7-routing/code-splitting.md)）。
这些都靠构建工具自动化。

## 怎么用：主流工具

### Webpack（传统霸主）
配置灵活、生态成熟，但配置复杂、冷启动慢。曾是标配，现多用于存量项目。

### Vite ★ 现代首选
- **开发时**：用原生 ESM，**不打包**（浏览器直接按模块加载），冷启动极快，HMR 秒级。
- **生产时**：用 Rollup 打包，产物优化好。
```
开发：源码 ─ESM─> 浏览器（按需编译，按需加载，快）
生产：源码 ─Rollup 打包─> 优化产物
```
> Vite 的精髓：**开发时不打包**（利用浏览器原生 ESM），所以项目再大启动也快。这解决了 Webpack 的"冷启动慢"痛点。

### esbuild / Rollup / Turbopack
- **esbuild**：Go 写的极快打包器，Vite 开发时用它转译。
- **Rollup**：产出干净、Tree-shaking 好，Vite 生产用它。
- **Turbopack**：Next.js 的新打包器（Rust），主打增量构建快。

### Dev vs 生产构建的区别 ★
| | 开发（dev） | 生产（build） |
|---|---|---|
| 目标 | 快速反馈、好调试 | 体积小、运行快 |
| 是否打包 | Vite 不打包（ESM） | 打包 |
| Source Map | 完整（好调试） | 隐藏/精简（防泄露，呼应当前[01-11](../01-11-security/other-security.md)） |
| 压缩 | 不压缩 | 压缩 |
| Tree-shaking | 关 | 开 |

> 同一份代码，开发和生产构建策略完全不同——开发为"人"，生产为"机器/用户"。

## 常见坑

- ❌ **开发能跑生产崩**：开发时未做 Tree-shaking/压缩，掩盖了某些问题（如依赖了被 shake 掉的副作用）。
  - ✅ 正例：上线前一定跑生产构建测一遍。
- ❌ **忽视构建配置的安全**：生产部署了 sourcemap 泄露源码（呼应当前[01-11](../01-11-security/other-security.md)）。
- ❌ **构建太慢不优化**：大型项目构建几分钟，开发体验差。用 Vite/增量构建/缓存优化。
