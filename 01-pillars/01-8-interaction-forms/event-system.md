# 事件系统（Event System）

> 没有交互的网页只是静态文档。用户的一切操作——点击、输入、滚动——都是事件。理解事件系统（流、委托、合成事件），才能正确处理用户输入，也为后面的表单、手势打基础。

## 是什么

事件系统指浏览器**捕获用户与浏览器交互**的机制。核心概念：

| 概念 | 含义 |
|---|---|
| **事件流** | 事件传播的路径：捕获阶段 → 目标 → 冒泡阶段 |
| **事件委托** | 利用冒泡，在父元素统一处理子元素的事件 |
| **合成事件** | 框架（React）对原生事件的包装 |

一句话边界：**事件是"发生了什么"的通知，事件系统决定"通知怎么传、谁来处理"。**

## 为什么：理解事件流才能正确处理交互

### 事件流的三阶段
```
捕获阶段（Capture）：从 window 往下，逐层到目标元素的祖先
  → 目标阶段（Target）：事件到达被点击的元素
    → 冒泡阶段（Bubble）：从目标往上冒，逐层到 window
```
大多数事件**冒泡**（从目标往上）。点击一个按钮，它的父、祖父……都会收到这个点击事件。这就是为什么"点子元素，父元素的 onClick 也会触发"。

> 事件流的意义：它让你能选择"在哪一层处理事件"。可以在目标处理（直接绑子元素），也可以在祖先处理（事件委托）。

### 事件委托 ★ 实用技巧
利用冒泡：不给每个子元素绑事件，而是在**父元素绑一个**，通过 `event.target`（实际被点的元素）判断是谁：
```
❌ 给 100 个 li 各绑 click（100 个监听器）
listItems.forEach(li => li.addEventListener('click', handler))

✅ 在父 ul 绑一个，靠冒泡统一处理（1 个监听器）
ul.addEventListener('click', e => {
  if (e.target.matches('li')) handler(e.target)   // 判断点的是不是 li
})
```
**价值**：
- **性能**：1 个监听器 vs 100 个。
- **动态友好**：后续新增的 li 自动被处理（不用再单独绑定）。
> 这正是 React 合成事件的底层思路——在根节点统一委托。

### 合成事件（Synthetic Event）
框架（React）不直接用原生事件，而是包装成**合成事件**：
- **统一接口**：屏蔽浏览器差异（如 IE 与标准的差异），提供一致的 API。
- **性能（事件委托）**：React 17+ 在根节点统一绑一个监听器，靠冒泡派发到对应组件的处理器——这就是事件委托的大规模应用。
- **与渲染同步**：合成事件保证事件处理与 React 渲染状态一致。

## 怎么用

### 阻止冒泡与默认行为
```
e.stopPropagation()    // 阻止事件继续冒泡（祖先收不到）
e.preventDefault()     // 阻止默认行为（如链接跳转、表单提交刷新）
```
- `stopPropagation`：模态框内点击不触发背后遮罩的关闭逻辑。
- `preventDefault`：阻止 `<a>` 跳转、阻止表单默认提交（改用 AJAX）。

> 注意：`stopPropagation` 别滥用——它会让事件流不可预测，上层组件预期收到事件却收不到。只在确有需要时用。

### React 的合成事件
```
// React 用 onClick（驼峰），底层是合成事件
<button onClick={e => { console.log(e.target) }}>点击</button>
// e 是合成事件，e.target 是真实 DOM，e.preventDefault/stopPropagation 可用
```

## 常见坑

- ❌ **给大量同类元素各绑事件**：性能差。用事件委托。
- ❌ **滥用 stopPropagation**：让事件流不可预测，上层逻辑收不到事件，难调试。
- ❌ **忘 preventDefault 导致表单刷新**：表单提交默认刷新整页，要在处理器里 preventDefault 改 AJAX。
- ❌ **混淆 e.target 和 e.currentTarget**：`target` 是实际触发元素（冒泡时可能是子元素），`currentTarget` 是绑监听器的元素。
