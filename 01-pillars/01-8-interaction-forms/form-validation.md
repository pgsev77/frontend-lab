# 表单校验（Form Validation）

> "邮箱格式对不对、必填有没有填、密码够不够强"——校验是表单的核心职责。校验的时机、方式、展示，直接影响用户体验。

## 是什么

表单校验指**验证用户输入是否符合规则，并给出反馈**。按时机和方式分：

| 维度 | 选项 |
|---|---|
| **时机** | onChange（每次输入）/ onBlur（失焦）/ onSubmit（提交时） |
| **同步/异步** | 同步（格式/必填）/ 异步（唯一性/查服务端） |
| **展示** | 字段级（输入框旁）/ 表单级（顶部汇总） |

一句话边界：**校验不只是"判断对错"，还包括"什么时候验、怎么告诉用户"。**

## 为什么：校验时机影响体验

### onChange：即时但可能打扰
每次输入都校验。优点：用户立刻知道问题。缺点：用户输到一半（如邮箱还没输完）就报"格式错误"，很打扰。

### onBlur：折中 ★ 常用
输入框失焦时校验。用户输完一个字段、移到下一个时才提示，既及时又不打扰。**多数场景的最佳选择。**

### onSubmit：集中
提交时一次性校验所有字段。优点：不打扰输入过程。缺点：用户填完一堆才发现错误，要回滚修改，体验差。适合简单表单或作为最后兜底。

> 实践：**onBlur 做字段校验 + onSubmit 做全表兜底校验**，两者结合最佳。

## 怎么用

### 同步校验
格式、必填、长度等本地能判的，用校验 schema 描述：
```
// 用 Zod 定义 schema（声明式，可复用）
const schema = z.object({
  email: z.string().email('邮箱格式错误'),
  age: z.number().min(18, '必须满 18 岁'),
  password: z.string().min(8, '至少 8 位')
})
// 表单库集成 schema，自动校验 + 错误信息
```
**为什么用 schema 库（Zod/Yup/Valibot）**：
- 声明式描述规则，可读性强。
- 一份 schema 同时用于前端校验和后端校验（前后端共享，呼应 [03 前后端协作](../../03-engineering/README.md)）。
- 类型推导：schema 自动生成 TypeScript 类型（类型即契约）。

### 异步校验
需要查服务端的（如用户名是否被占用），异步校验：
```
// 注册时检查用户名唯一性
const { register } = useForm()
<input {...register('username', {
  validate: async (value) => {
    const exists = await checkUsername(value)   // 异步查服务端
    return !exists || '用户名已被占用'
  }
})} />
```
**注意**：异步校验要配合 [防抖](./interaction-feedback.md)，避免每输一个字符就请求服务器。

### 错误展示
- **字段级**：错误信息显示在对应输入框下方，就近原则，用户不用猜哪个字段错了。
- **明显的视觉提示**：错误用红色/图标，但别只靠颜色（色盲友好，呼应 [01-10](../01-10-accessibility-multiplatform/README.md)）。
- **可访问性**：错误信息用 `aria-describedby` 关联到输入框，屏幕阅读器能读出（呼应 [01-10 a11y](../01-10-accessibility-multiplatform/README.md)）。

## 常见坑

- ❌ **onChange 校验打扰输入**：邮箱输一半就报错。
  - ✅ 正例：用 onBlur，输完才校验。
- ❌ **只前端校验**：前端校验绕过容易，后端必须再校验一遍（安全 + 数据完整性）。呼应 [01-11 安全](../01-11-security/README.md)。
- ❌ **异步校验不防抖**：每输一个字符请求一次服务器，浪费且可能被限流。
  - ✅ 正例：异步校验配防抖。
- ❌ **错误信息技术化**：显示"ValidationError: string.invalid"，用户看不懂。
  - ✅ 正例：人类可读的错误信息。
