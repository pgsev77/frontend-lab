# 国际化与本地化（i18n & l10n）

> 让产品走向全球，不只是"翻译文字"——还有日期格式、货币、复数规则、文字方向（阿拉伯语从右到左）。忽视这些，国际用户的体验会很糟。

## 是什么

- **i18n（Internationalization）**：**架构上**让产品支持多语言/多地区（把文案抽出、支持不同格式）。
- **l10n（Localization）**：**具体翻译和适配**某个语言/地区（翻译文案、调整格式）。

一句话边界：**i18n 是"做好支持多语言的准备"，l10n 是"实际翻译某语言"。** 先 i18n 再 l10n。

## 为什么：国际化要解决的四个问题

### 1. 文案不能硬编码
```
❌ <button>提交</button>                    // 写死，换语言改不了
✅ <button>{t('submit')}</button>           // 文案从翻译文件取
```
所有面向用户的文案都要提取，通过 i18n 库（如 react-intl、i18next）按当前语言取。

### 2. 格式因地而异
同样的数据，不同地区格式不同：
| 数据 | 美国 | 中国 | 德国 |
|---|---|---|---|
| 日期 | 12/31/2024 | 2024/12/31 | 31.12.2024 |
| 数字 | 1,234.56 | 1,234.56 | 1.234,56 |
| 货币 | $1,234.56 | ¥1,234.56 | 1.234,56 € |
用 `Intl` API（`Intl.NumberFormat`/`Intl.DateTimeFormat`）按地区格式化，别手拼。

### 3. 复数/性别规则不同
英文 one apple / two apples（单复数），阿拉伯语有六种复数形式，俄语复数规则更复杂。用 ICU MessageFormat 让翻译处理复数：
```
{count, plural, one {# 条评论} other {# 条评论}}   // 库会按语言选对形式
```

### 4. 文字方向（RTL）★
阿拉伯语、希伯来语从**右到左（RTL）**书写。整个布局要镜像：
- 用**逻辑属性**（`margin-inline-start`）而非物理属性（`margin-left`），自动适配方向。详见 [01-3 现代布局](../01-3-styling/modern-layout.md)。
- 设 `<html dir="rtl">`，配合逻辑属性，布局自动镜像。

## 怎么用：i18n 的关键实践

### 文案提取与翻译文件
```
// zh.json: { "submit": "提交" }
// en.json: { "submit": "Submit" }
// ar.json: { "submit": "إرسال" }
const { t } = useTranslation()
<button>{t('submit')}</button>
```

### 用 Intl 格式化
```
new Intl.NumberFormat('de-DE').format(1234.56)   // "1.234,56"
new Intl.DateTimeFormat('zh-CN').format(date)     // "2024/12/31"
```

### 布局要为翻译预留空间 ★
翻译后文本长度变化大（德语比中文长 30%，阿拉伯语可能更长）：
- ❌ 固定宽度的按钮：英文 "Submit" 翻译德语 "Absenden" 撑爆。
- ✅ 弹性宽度、文本截断（ellipsis）、留足空间。

## 常见坑

- ❌ **硬编码文案**：到处写死中文，后期国际化要重构。
  - ✅ 正例：从一开始就提取文案，即使暂时只一种语言。
- ❌ **手拼日期/数字格式**：换个地区格式就错。
  - ✅ 正例：用 Intl API。
- ❌ **忽视 RTL**：做不了阿拉伯语市场。用逻辑属性。
- ❌ **忽视翻译长度变化**：固定宽度布局翻译后撑爆。
