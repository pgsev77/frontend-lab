# 测试的实践原则（Testing Principles）

> 会写测试不难，难的是"写对的测试"。太多测试是负担——维护贵、重构就断、却没真正防住 bug。这篇提炼测试的原则，让测试真正有价值而非负担。

## 是什么

测试实践原则指**怎么判断"该测什么、怎么测、测到什么程度"**的指导。核心是让测试**高价值、低维护成本**。

一句话边界：**好测试防 bug 且不拖累迭代；坏测试又脆又没用，成了负担。**

## 为什么：测试的常见误区

### 误区 1：追求 100% 覆盖率
覆盖率只表示"代码被执行过"，不表示"行为被验证"。`if(x){...}` 即使两个分支都跑过，也可能没断言对。盲目追 100% 产出大量低价值测试，维护成本高。

### 误区 2：测实现细节
测"调了某内部方法""state 是某值"。实现一重构测试全挂，但重构本不该破坏行为。这种测试拖累迭代而非保护它。

### 误区 3：测试和实现同构
测试只是把实现逻辑抄一遍。实现错了，测试也"按错的预期"通过，没防住 bug。

## 怎么用：五条原则

### 1. 测行为，不测实现 ★
- ✅ 测"用户输入 X，组件显示 Y""调用 API 后状态变成 Z"——这是行为/结果，稳定。
- ❌ 测"调用了某内部函数""state 经过哪些中间值"——这是实现，易变。
呼应当前[01-13 测试](./testing.md) 的 Testing Library 哲学。

### 2. 测边界与异常，别只测正常路径
bug 多在边界（空、null、极大值、并发）和异常（失败、超时）。只测"正常输入→正常输出"的测试，防不住真实 bug。

### 3. 测试应独立可重复
每个测试不依赖其他测试的副作用、不依赖执行顺序。这样任何一个失败都能独立复现定位，不会"整体跑通过单独跑挂"。
```
❌ 测试A创建数据，测试B依赖A的数据（顺序依赖）
✅ 每个测试自己 setup 自己的数据，互不依赖
```

### 4. AAA 模式
```
Arrange（准备）：构造输入和前置条件
Act（执行）：调用被测对象
Assert（断言）：验证结果
```
清晰的测试结构，一眼看懂"测什么、怎么测、期望什么"。

### 5. Mock 的正确态度 ★
Mock 是双刃剑：让测试快且隔离，但过度 mock 让测试"测的是 mock 不是真实代码"。
- **Mock 外部依赖**（API、第三方）——合理，测试不该依赖网络。
- **Mock 被测对象自己的内部**——危险，等于没测真实逻辑。
- 用 MSW（Mock Service Worker）拦截请求，比逐个 mock 函数更接近真实。
- 呼应当前[01-6 数据获取](../01-6-data-fetching/README.md)：测试时 mock API。

## 怎么用：测什么不测什么

### 该测
- 复杂的纯逻辑（计算、转换、状态机）——单元测试主力。
- 关键组件的交互行为——组件测试。
- 核心业务流程——E2E。
- 边界和错误处理。

### 不该测（或低优先级）
- 简单的 getter/setter、纯展示无逻辑的组件——测了收益低。
- 框架本身（别测"React 的 useState 会不会工作"）。
- 第三方库（它们有自己的测试）。

## 常见坑

- ❌ **追 100% 覆盖率**：产出低价值测试。覆盖关键行为优先。
- ❌ **测实现细节**：重构就断。
- ❌ **测试互相依赖**：难定位、难复现。
- ❌ **过度 mock**：测了 mock 没测真实。
