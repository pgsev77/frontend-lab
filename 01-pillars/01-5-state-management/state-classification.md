# 状态分类（State Classification）

> 这是状态管理的**第一步，也是最重要的一步**。前端最常见的混乱，就是"把所有状态都当成一种东西来管"。分类清楚了，该用什么工具、放在哪里，自然就清楚了。

## 是什么

前端的状态（State）按"来源和归属"分成几类，性质完全不同，**该用不同的方式管理**：

| 类型 | 谁拥有 | 例子 | 管理方式 |
|---|---|---|---|
| **UI 状态** | 前端自管 | 当前 Tab、弹窗开关、输入焦点 | 组件 state / 局部 store |
| **服务端状态** | 后端拥有，前端缓存 | 用户列表、订单详情 | TanStack Query / SWR |
| **URL 状态** | URL 本身 | 路由、查询参数、筛选条件 | 路由库，放进 URL |
| **本地持久状态** | 浏览器存储 | 用户偏好、草稿 | localStorage / IndexedDB |
| **临时状态** | 即弃 | 提交前的表单输入 | 组件 state |

一句话边界：**不是所有状态都该进 Redux。状态分类决定它归谁管、用什么工具。** 混淆类型是状态混乱的根源。

## 为什么：分类为什么是第一步

### 痛点：把服务端状态当客户端状态管
这是前端最经典的错误。把接口数据塞进 Redux/Zustand，然后到处手动 `refetch`、手动判断"数据是不是最新的"。结果是写了一大堆模板代码，还经常显示过时数据。

**根本原因**：服务端状态**不是你的**——你只是缓存了一份后端的数据。它的"真理"在后端，前端随时可能过时。把它当客户端状态管，等于假装"我拥有它"，于是陷入无尽的手动同步。

> 这正是 [00-2 权衡](../../00-foundation/tradeoffs.md) 第二组的核心命题：**客户端状态 vs 服务端状态，谁才是真理**。区分两者是 [01-6 数据获取](../01-6-data-fetching/README.md) 的前提。

### 痛点：把 URL 状态藏在 store 里
当前页码、当前筛选条件，本来该放进 URL（可分享、可刷新、可后退）。但很多人塞进 Redux，结果：链接分享给别人变成第一页、刷新丢失筛选。

**根本原因**：没意识到"URL 本身就是一种状态存储"，而且是最该用的那种（因为它自带可分享/可刷新/可后退）。

## 怎么用：决策清单

拿到一个状态，按这个顺序问：

1. **它来自后端吗？** → 服务端状态，用 Query 库（[01-6](../01-6-data-fetching/README.md)），别用 Redux。
2. **它应该可分享/可刷新保留吗？**（页码、筛选、Tab） → URL 状态，放进 URL（[01-7 路由](../01-7-routing/README.md)）。
3. **它要跨刷新保留吗？**（用户偏好） → 本地持久，存 localStorage。
4. **它是纯 UI 交互、且局部使用吗？**（弹窗开关、输入值） → UI 状态，组件 state。
5. **多个组件要共享吗？** → 考虑提升到共同祖先或全局 store（见 [状态架构](./state-architecture.md)）。

### 各类状态的特点
- **UI 状态**：可信、即时、前端完全控制。用 useState/Zustand。
- **服务端状态**：**可能过时**、多端共享、需同步。用 TanStack Query，它内置缓存失效/重新获取/竞态处理。
- **URL 状态**：可分享、可刷新、可后退。**能用 URL 就别用 store。**
- **本地持久**：跨会话保留。注意序列化与版本兼容。

## 常见坑

- ❌ **把接口数据塞进 Redux**：手动 refetch、手动判过期、手动同步，陷入泥潭。
  - ✅ 正例：服务端状态交给 Query 库，它专门解决这些问题。
- ❌ **把筛选条件藏进 store**：链接分享丢失筛选，刷新回到第一页。
  - ✅ 正例：筛选/分页/Tab 放进 URL 查询参数。
- ❌ **所有状态都全局化**：一个弹窗开关也放全局 store，过度设计。
  - ✅ 正例：局部 UI 状态用组件 state，只把真正跨组件共享的提升。
- ❌ **状态分类不清导致重复存储**：同一份数据既在 store 又在 URL，两边打架。
