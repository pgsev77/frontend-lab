# 服务端渲染与同构（SSR / SSG / ISR / RSC）

> SPA（单页应用）解决了体验流畅，却带来 SEO 差、首屏白屏的新问题。服务端渲染重新把"首屏在服务端生成"拉回来，但用现代方式——同构。这是从 SPA 走向"既要体验又要首屏/SEO"的关键跃迁。

## 是什么

几种渲染模式的对比：

| 模式 | HTML 在哪生成 | 首屏 | SEO | 特点 |
|---|---|---|---|---|
| **CSR（客户端渲染）** | 浏览器（SPA） | 慢（等 JS） | 差 | 体验流畅 |
| **SSR（服务端渲染）** | 服务器（每次请求） | 快 | 好 | 服务器压力 |
| **SSG（静态生成）** | 构建时 | 最快 | 好 | 内容固定时最优 |
| **ISR（增量静态再生）** | 构建时 + 后台更新 | 快 | 好 | SSG + 动态更新 |
| **RSC（React 服务端组件）** | 服务器（组件级） | 快 | 好 | 新范式 |

一句话边界：**SPA 首屏慢/SEO 差，SSR/SSG 在服务端先生成首屏 HTML 解决这两点，"同构"让同一份代码跑两端。**

## 为什么：SPA 的根本局限

CSR（SPA）流程：浏览器下载空 HTML + JS → JS 执行 → 请求数据 → 渲染。问题：
- **首屏慢**：要等 JS 下载执行 + 数据请求，期间白屏。
- **SEO 差**：爬虫拿到的是空 HTML（内容靠 JS 渲染），抓不到内容。
- **弱机更惨**：低端机执行 JS 慢，首屏更慢。

服务端渲染把"首屏 HTML 生成"移到服务器：服务器拿数据、渲染好 HTML 直接返回，浏览器拿到就有内容。首屏快、爬虫能看到内容。

## 怎么用：同构与水合

### 同构（Isomorphic）
**同一份组件代码既能在服务端跑（生成 HTML），又能在客户端跑（接管交互）**。开发者写一次，两端共用。

### 水合（Hydration）★ 关键且易错
服务器返回了"已渲染的 HTML"，但它是静态的（无事件）。客户端 JS 加载后，要**接管**这份 HTML，把事件监听器附加上，让它变成可交互的 SPA。这个过程叫水合。
```
服务器：渲染组件 → 生成 HTML（静态） → 返回
浏览器：显示 HTML（首屏立即可见） → 下载 JS → 水合（附加事件）→ 可交互
```
**水合的坑**：
- **水合不一致（mismatch）**：服务端和客户端渲染结果不一致（如用了 `Date.now()`、`Math.random()`、读 window），React 报警告甚至重建 DOM。**SSR 代码不能用浏览器专属 API**（window/document），或要做守卫。
- **水合成本**：客户端要把整棵树水合，大页面水合本身也耗时（INP 受影响）。
- **选择水合/部分水合/RSC**：新版用 RSC 减少水合量，只对真正交互的部分水合。

### 各模式选型
| 场景 | 推荐 |
|---|---|
| 内容站（博客/文档/营销页） | **SSG**（构建时生成静态，最快） |
| 电商/新闻（内容常更新） | **ISR**（静态 + 后台再生） |
| 个性化仪表盘（需登录态） | **SSR** 或 CSR |
| 强交互应用（后台管理） | **CSR** 够用（SEO 不重要） |

### RSC（React Server Components）★ 新范式
RSC 把"组件"分服务端组件和客户端组件：
- **服务端组件**：在服务器渲染，**不发 JS 到客户端**（0 客户端开销），可直接访问数据库/文件系统。
- **客户端组件**：带交互的，发到客户端水合。
> RSC 的价值：把"该在服务端跑的"留在服务端（不增加 bundle），只把"该交互的"发客户端。是 SSR 的演进——从"整页渲染"到"组件级按需渲染"。详见 [01-7 数据路由](../01-pillars/01-7-routing/data-routing.md) 与 [01-4 渲染调度](../01-pillars/01-4-rendering/rendering-scheduling.md)。

### 流式渲染（Streaming SSR）
配合 Suspense，服务器**边渲染边发送**：先发已就绪的部分，数据未到的部分用 fallback 占位，数据到了再流式补上。用户更早看到内容。详见 [01-4 渲染调度](../01-pillars/01-4-rendering/rendering-scheduling.md)。

## 常见坑

- ❌ **SSR 用了浏览器 API**：window/document 在服务端不存在，崩。要做守卫或挪到 effect 里。
- ❌ **水合 mismatch**：服务端客户端渲染不一致，React 重建 DOM，浪费。保证两端一致（避免时间/随机/客户端专属逻辑）。
- ❌ **盲目全 SSR**：后台管理等不需 SEO 的应用也 SSR，增加服务器复杂度却无收益。
- ❌ **忽视水合性能**：大页面水合慢影响 INP。用部分水合/RSC 减少。
