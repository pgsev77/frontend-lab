# 复杂度从何而来

> 后端的复杂度来自状态分布、并发、部分失败、网络不可靠、时间顺序；**前端的复杂度来源完全不同**。本篇把前端的复杂性拆成五个来源——理解它们，你就能在面对任何混乱的前端代码时，定位"乱"到底乱在哪。

## 是什么

前端的复杂度（也就是"为什么前端代码写着写着就乱了"）主要来自五个来源。它们和 [两条主轴](./two-axes.md) 紧密对应：前三个落在两轴及其交汇上，后两个横切整个系统。

## 为什么：五个复杂度来源

### 来源 1：状态与视图的同步难题（落在两轴交汇）

这是**声明式 UI 的核心代价**。声明式 UI 的承诺是"你只管描述状态，框架保证视图一致"——但这个保证背后是巨大的复杂性：

- 一个状态变了，**哪些视图该更新？更新到什么程度？**
- 多个状态相互依赖，改一个引发连锁更新，怎么避免死循环或漏更新？
- 状态来自多个地方（组件内、全局、URL、服务端），视图怎么把它们正确合并？

> 派生技术：响应式系统、虚拟 DOM 与调和（Reconciliation）、重渲染控制（memo/依赖数组）、不可变数据。详见 [01-4 渲染机制](../01-pillars/01-4-rendering/README.md) 和 [01-5 状态管理](../01-pillars/01-5-state-management/README.md)。

### 来源 2：异步带来的时间错位（落在状态轴）

前端的时间线是**混乱的**：

- 用户点了按钮，但接口数据还没回来——界面该显示什么？
- 用户连点两次，第一个请求还没回，第二个先回了——怎么保证显示的是最新结果（竞态）？
- 数据加载中、加载成功、加载失败、加载了但为空——这"四态"每个都要处理界面。

> **时间错位**是前端区别于静态页面、也区别于后端的关键难点。后端是"请求-响应"的线性流程；前端是"用户随时操作 × 数据异步到达 × 网络随时失败"的多线交织。派生技术：异步状态管理（loading/error/data 三态）、竞态处理（AbortController/请求 ID）、乐观更新、防抖节流。详见 [01-6 数据获取](../01-pillars/01-6-data-fetching/README.md) 和 [01-8 交互与表单](../01-pillars/01-8-interaction-forms/README.md)。

### 来源 3：规模化的视图与状态组织（落在视图轴）

当一个应用长到上千个组件、几十个页面、几十种状态，**组织本身就成了最大的难题**：

- 组件怎么拆？拆太细耦合多，拆太粗不可复用。
- 状态放哪？全局还是局部？哪些该提升、哪些该下沉？
- 样式怎么管？全局 CSS 会冲突，CSS-in-JS 有开销，原子化 CSS 要学约定。
- 路由怎么组织？嵌套层级、数据加载、代码分割如何配合？

> 这是前端"架构"的主战场。后端架构难在分布式；前端架构难在"视图与状态的规模化组织"。派生技术：组件化与组合模式、状态架构、CSS 架构、路由架构。详见 [01-2 组件化](../01-pillars/01-2-componentization/README.md)、[01-3 样式](../01-pillars/01-3-styling/README.md)、[01-12 架构与工程化](../01-pillars/01-12-architecture-engineering/README.md)。

### 来源 4：多端多形态（横切）

同一份前端逻辑，要在不同地方跑，且表现一致：

- **Web vs 移动 H5 vs SSR**：同样的组件，在浏览器、在手机、在服务端渲染，行为可能不同（如 `window` 在 SSR 不存在）。
- **不同浏览器/设备**：Chrome、Safari、旧版 Edge、各种国产浏览器，API 支持参差。
- **不同屏幕**：从 320px 手机到 4K 显示器，布局都要合理。

> 派生技术：响应式设计、SSR/同构、兼容与降级（polyfill/特性检测）、渐进增强。详见 [01-10 可访问性与多端](../01-pillars/01-10-accessibility-multiplatform/README.md) 和 [02 前端进阶](../02-advanced/README.md)。

### 来源 5：不可控环境（横切）

前端运行的环境**全部不可控**，这是和后端最鲜明的对比：

- **网络不可控**：用户会断网、会切弱网、请求会超时——界面不能崩。
- **设备不可控**：内存小的手机、性能差的 CPU——动画可能卡、页面可能崩。
- **用户不可控**：狂点、回退、关页面、改 URL——任何操作都不能让状态错乱。
- **浏览器不可控**：缓存策略、扩展插件、隐私模式——行为可能出乎意料。

> 派生技术：防御性编程、错误边界、离线处理（PWA/Service Worker）、兼容降级。这是 [防御性哲学](./frontend-essence.md) 的直接来源。

## 五个来源与两条主轴的对应

| 复杂度来源 | 落在哪 |
|---|---|
| 状态与视图同步 | 两轴交汇（核心） |
| 异步时间错位 | 状态轴 |
| 规模化组织 | 视图轴 |
| 多端多形态 | 横切 |
| 不可控环境 | 横切 |

> 记住这个对应关系：当你面对一段混乱的前端代码，先问"它的复杂度来自这五个里的哪一个"，就能定位问题、对症下药，而不是盲目重构。

## 常见误区

- ❌ **以为前端复杂度只是"组件多了"**：组件多是表象，根因是状态与视图的同步、异步时间错位等深层来源。
- ❌ **用"性能优化"解决所有问题**：很多"卡"其实是状态管理混乱导致的无谓重渲染，根因在来源 1，而非性能本身。
- ❌ **忽视异步四态**：只写了"成功"的界面，loading/error/空状态全靠用户运气。
