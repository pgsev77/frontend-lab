# 两条主轴（心智锚点）

> 这是整个知识体系**最重要的认知工具**。前端概念浩如烟海（组件、状态、虚拟 DOM、重渲染、SSR、Hooks、路由、Core Web Vitals……），如果只一个个记"它是什么"，会学得很散、很容易忘。两条主轴给你一个**归位的坐标系**——任何前端知识点，都能在这里找到位置。

## 是什么

前端的所有问题，本质上只围绕**两条轴**展开：

| 轴 | 核心问题 | 通俗版 |
|---|---|---|
| **视图轴** | 界面怎么描述 · 怎么组织 · 怎么渲染 · 怎么不卡 | "界面怎么搞" |
| **状态轴** | 数据从哪来 · 怎么存 · 怎么变 · 怎么同步到视图 | "状态怎么搞" |

把这两条轴装进脑子，等于装了一个"知识索引"：遇到任何新概念，先问一句——**它属于视图轴还是状态轴？** 归位之后，它和已学概念的关系就清楚了。

## 为什么：两条轴从哪来

回到 [前端的本质](./frontend-essence.md)。前端有五个根本差异，但仔细看，它们其实只在回答两类问题：

- 一类关于**视图/界面**：界面要被直接感知、要适配各种环境、要在规模下被组织 → 这是**视图轴**（派生自差异 1、3、5）。
- 一类关于**状态/数据**：前端是后端的投影、要应对异步与用户行为 → 这是**状态轴**（派生自差异 2、4）。

也就是说，两条主轴不是凭空抽象，而是从前端的本质差异里**自然长出来的两个切面**。前端的全部复杂性，都在这两个切面上展开。

### 交互：两条轴的交汇

前端最核心的闭环是**交互**，而交互恰好是两条轴的交汇点：

```
用户操作（点击/输入）
    │
    ▼
改变状态（状态轴：怎么变）   ← 01-8 交互与表单落在这里
    │
    ▼
状态变化触发视图更新（视图轴：怎么渲染）
    │
    ▼
视图响应，用户看到反馈
    │
    ▼
（下一个操作……）
```

这个闭环（操作 → 状态 → 视图 → 响应）就是前端区别于"静态页面"的根本特征。它也解释了为什么 [01-8 交互与表单](../01-pillars/01-8-interaction-forms/README.md) 不专属任何一条轴——它就是**两条轴交汇的地方**。

> 这和后端的结构完全同构：后端的"幂等/缓存"是数据轴和请求轴的胶水；前端的"交互"是视图轴和状态轴的胶水。跨轴的地方，往往是最难的。

## 怎么用：归位练习（最关键的部分）

光记住两条轴没用，关键是要练成"遇到概念就归位"的本能。下面用一组例子示范：

### 例 1：虚拟 DOM（Virtual DOM）
- **它解决什么问题**：在状态变化后，高效地算出界面需要怎么变，避免直接、昂贵地操作真实 DOM。
- **归位**：视图轴（"怎么渲染"）。
- **理解**：虚拟 DOM 是视图轴上"高效更新界面"的工具——它是渲染机制的实现手段。

### 例 2：状态管理（State Management）
- **解决什么**：让多个组件能共享和同步同一份状态，且变化可追踪。
- **归位**：状态轴（"怎么存、怎么变、怎么同步到视图"）。
- **理解**：状态管理是状态轴的"中枢"——它决定了数据如何流动到视图。

### 例 3：组件（Component）
- **解决什么**：把界面拆成可独立、可复用的单元。
- **归位**：视图轴（"怎么组织"）。
- **理解**：组件是视图轴上"组织规模化界面"的基本单元。

### 例 4：React Hooks（如 useState/useEffect）
- **解决什么**：让函数组件能"挂载"状态和副作用，连接状态轴与视图轴。
- **归位**：**跨轴**。`useState` 在状态轴（管理状态），但它驱动视图轴的重渲染；`useEffect` 在状态轴（处理副作用），却影响视图（数据获取后更新）。
- **理解**：Hooks 是连接两条轴的"胶水"——没有它，函数组件只能是静态的视图轴单元。

### 例 5：路由（Routing）
- **解决什么**：根据 URL 显示对应的界面，让"页面"可分享、可后退、可刷新。
- **归位**：**跨轴**。它决定显示哪个视图（视图轴），但 URL 本身是状态（状态轴："URL 即状态"）。
- **理解**：路由是把"界面位置"状态化的工具，横跨两轴。

### 例 6：性能优化（如 React.memo / 防抖）
- **解决什么**：减少不必要的计算和渲染，让界面更流畅。
- **归位**：视图轴（"怎么不卡"，减少重渲染）+ 状态轴（"怎么变"，控制触发频率）。
- **理解**：性能优化常常是**两轴协同**——既要减少视图重渲染，又要控制状态变化的粒度。

### 归位方法论
做归位时，问三个问题：
1. **这个概念处理的是"界面长什么样/怎么渲染"还是"数据怎么流动"？** → 定主轴
2. **它解决这条轴上的哪个子问题？**（描述/组织/渲染/不卡，或 来/存/变/同步）
3. **它有没有触及另一条轴？** → 有就是跨轴概念，往往是最关键的（因为连接两条轴，决定整体效率）

## 横切概念：不专属任何一条轴

有些概念不专门服务某条轴，而是**服务于"整个前端系统"**：

| 横切概念 | 作用 |
|---|---|
| **性能与体验**（01-9） | 让两条轴都"快"且"感觉快" |
| **可访问性与多端**（01-10） | 让两条轴适配各种环境和所有人 |
| **安全**（01-11） | 守住两条轴的边界（防 XSS、防 CSRF、令牌存储） |
| **架构与工程化**（01-12） | 决定两条轴的代码怎么组织、怎么构建 |
| **可观测性与质量**（01-13） | 检验两条轴的产出（监控、测试、质量门禁） |

所以本体系的 13 个支柱，可以这样理解：
- 视图轴主力：[01-1 视图基础](../01-pillars/01-1-view-fundamentals/README.md)、[01-2 组件化](../01-pillars/01-2-componentization/README.md)、[01-3 样式](../01-pillars/01-3-styling/README.md)、[01-4 渲染机制](../01-pillars/01-4-rendering/README.md)
- 状态轴主力：[01-5 状态管理](../01-pillars/01-5-state-management/README.md)、[01-6 数据获取](../01-pillars/01-6-data-fetching/README.md)、[01-7 路由](../01-pillars/01-7-routing/README.md)
- 两轴交汇：[01-8 交互与表单](../01-pillars/01-8-interaction-forms/README.md)
- 横切：[01-9 性能体验](../01-pillars/01-9-performance-ux/README.md)、[01-10 可访问性多端](../01-pillars/01-10-accessibility-multiplatform/README.md)、[01-11 安全](../01-pillars/01-11-security/README.md)、[01-12 架构工程化](../01-pillars/01-12-architecture-engineering/README.md)、[01-13 可观测质量](../01-pillars/01-13-observability-quality/README.md)

## 常见误区

- ❌ **以为两条轴是割裂的**：实际上大量概念跨轴（Hooks、路由、性能优化）。跨轴概念之所以重要，恰恰因为它连接两条轴、决定整体效率。
- ❌ **死记归位结果**：归位是思维工具，不是考点。目的是建立直觉，不是为了给概念贴标签。
- ❌ **遇到新概念就慌**：任何前端新概念（哪怕没见过），先问"它处理视图还是状态"，就找到了思考的起点。
