# 贯穿一切的权衡

> 前端没有"银弹"，每个技术选择都是**权衡**。本篇梳理贯穿前端始终的四组核心权衡——理解它们，你就能在面对任何选型时有判断依据，而不是盲从流行。

## 是什么

权衡（Tradeoff）是工程的核心：**为了得到 A，必须牺牲 B**。前端的所有"该用哪个""该怎么做"的问题，本质都是在不同权衡之间做选择。本篇提炼四组贯穿前端的两轴权衡，它们会反复出现在后续每个支柱里。

## 为什么：为什么权衡是前端的常态

回到 [前端的本质](./frontend-essence.md)——前端面临三重复杂性：不可控环境、用户感知、规模化组织。这三重复杂性相互拉扯：

- 想让体验最好 → 可能要加载更多资源 → 性能变差。
- 想让代码最灵活 → 抽象层变多 → 可读性、维护成本上升。
- 想让首屏最快 → 可能要放弃客户端丰富交互 → 体验下降。

**没有任何方案能同时最优化所有维度**。成熟的工程师不是"找到最优解"，而是"清楚知道自己在哪组权衡的哪个点，并为此负责"。

## 怎么用：四组核心权衡

### 权衡 1：声明式 vs 命令式

这是前端**最根本**的一组权衡，整个现代前端的演进都围绕它。

| | 声明式（Declarative） | 命令式（Imperative） |
|---|---|---|
| 思路 | 描述"界面该长什么样"，框架负责更新 | 自己写"怎么操作 DOM"（`el.appendChild()`） |
| 优点 | 可读、可预测、易维护、状态-视图一致性 | 精细控制、极致性能、无框架开销 |
| 缺点 | 有框架开销、特定场景性能不如手写 | 状态一多就失控、难维护 |
| 典型 | React / Vue / 现代框架 | jQuery / 原生 DOM 操作 |

> **核心洞察**：现代前端几乎一边倒选声明式，是因为**界面复杂度增长后，命令式的维护成本指数上升**。声明式用"框架的开销"换"状态-视图一致性的保证"。但在极致性能场景（动画、Canvas、列表滚动），命令式仍有用武之地。详见 [01-4 渲染机制](../01-pillars/01-4-rendering/README.md)。

### 权衡 2：客户端状态 vs 服务端状态

前端最常犯的错误，是**把所有状态都当成"客户端状态"来管**。实际上状态分两类，性质完全不同：

| | 客户端状态（Client State） | 服务端状态（Server State） |
|---|---|---|
| 谁拥有 | 前端自己 | 后端（前端只是缓存/投影） |
| 例子 | 当前选中的 Tab、表单输入、UI 开关 | 用户列表、订单详情、库存 |
| 特点 | 可信、可控、即时 | **可能过时**、需要同步、多端共享 |
| 工具 | useState / Zustand / Redux | TanStack Query / SWR |

> **核心洞察**：服务端状态**不是你的**，你只是缓存了一份。把它当客户端状态管，就会陷入"什么时候该重新拉取""数据是不是最新的"的无尽麻烦。区分两者是 [01-5 状态管理](../01-pillars/01-5-state-management/README.md) 和 [01-6 数据获取](../01-pillars/01-6-data-fetching/README.md) 的核心命题。

### 权衡 3：体验 vs 性能

"真的快"和"感觉快"是两件事，常常冲突：

| | 极致性能 | 极致体验 |
|---|---|---|
| 思路 | 少加载、少计算、首屏指标最优 | 加载态、动画、即时反馈、骨架屏 |
| 冲突点 | 为了首屏最快，可能延迟加载交互逻辑 → 首次点击有延迟 | 为了即时反馈，先渲染占位 → 实际数据还没到 |

> **核心洞察**：用户感知的"流畅"，是 [Core Web Vitals](../01-pillars/01-9-performance-ux/README.md)（LCP/FID/CLS）的综合，而非单一指标。有时牺牲一点真实性能、换来感知流畅（如骨架屏），整体体验更好。这就是"性能感知"哲学的由来。

### 权衡 4：现在成本 vs 未来成本（技术债）

这组权衡贯穿所有工程，前端尤甚：

| | 现在省事（快） | 现在扎实（慢） |
|---|---|---|
| 表现 | 复制粘贴、写巨型组件、不抽象 | 设计系统、组件化、规范化 |
| 短期 | 交付快 | 交付慢 |
| 长期 | 技术债累积，改动牵一发动全身 | 可维护、可复用、改动局部化 |

> **核心洞察**：技术债不是"不写好代码"，而是**用未来的成本换现在的速度**。合理的债是工具（YAGNI：用不上就别先抽象），失控的债是灾难。判断标准：这个"省事"是临时方案还是会长期存在？详见 [01-12 架构与工程化](../01-pillars/01-12-architecture-engineering/README.md)。

## 常见坑

- ❌ **追求"最优解"**：前端的每个选择都有代价。成熟的态度是"我知道我在牺牲什么"，而不是"我找到了最好的方案"。
  - ✅ 正确：明确写下"选 A 是因为 X，代价是 Y，我们接受 Y"。
- ❌ **把服务端状态当客户端状态管**：用 Redux 存接口数据，然后到处手动 `refetch`。
  - ✅ 正确：服务端状态交给 TanStack Query/SWR，客户端状态才用 Zustand/useState。
- ❌ **为了"性能"牺牲所有体验**：禁用所有动画、加载态，首屏指标好看了，但用户觉得"卡顿、无反馈"。
  - ✅ 正确：性能服务于体验，而非反过来。
